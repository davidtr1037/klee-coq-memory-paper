\section{Implementation}
\label{sec:implementation}

Our implementation consists of two main components:
a \coq (9.0.1) framework and an extension of the \SE engine.
Our \coq framework is based on~\cite{klee-rocq},
and it includes the definitions of the semantics (\Cref{sec:concrete-semantics,sec:symbolic-semantics}) and the theoretical foundation (\Cref{sec:program-safety,sec:proof-generation}).
It consists of roughly 40,000 lines of code (LOC),
excluding third-party dependencies (\eg CompCert~\cite{CompCert}).
For comparison,
this is more than twice the size of the framework of~\cite{klee-rocq}, which consists of roughly 18,000 LOC.
Our proof generation approach (\Cref{sec:proof-generation}) is implemented on top of \klee~\cite{klee},
a \emph{state-of-the-art} \SE engine operating on \llvm IR~\cite{llvm}.
%Currently, some of the SMT transformations used in \klee are not supported by our implementation,
%but we plan to support them in future versions.
%In the $\tgep$ instruction, our implementation currently supports the \opcode{nuw} attribute.
Thanks to our formalization efforts,
we found several implementation issues in \klee that relate to memory modeling, which we outline next.

%\subsection{Implementation Issues in \klee}
\textit{Issue 1: Inconsistent Modeling of the Index Type.}
\klee represents memory contents using SMT arrays of sort $\arraysort{\smtsort{32}}{\smtsort{8}}$, implying a 32-bit index type, but computes $\tgep$ offsets using 64-bit SMT expressions, implying a 64-bit index type.

\textit{Issue 2: Incorrect Interpretation of \textup{$\tgep$}.}
\klee does not account for overflows when computing $\tgep$ offsets and is therefore not fully compliant with the \llvm reference.
We fixed the offset computation to use the right index type ($\bvsort{32}$) and report an error upon overflow.

\textit{Issue 3: Incorrect Interpretation of Memory Allocations.}
The \llvm semantics define an allocation as undefined behavior when its size exceeds the largest signed integer representable by the index type, but \klee does not check this condition.

\textit{Issue 4: Incorrect Interpretation of Allocation Alignment.}
For dynamic allocations (\eg \textit{malloc}), \klee uses a predefined alignment rather than the alignment specified by the corresponding instruction's \code{align} attribute.

\textit{Issue 5: Silent Truncation in Memory Allocations.}
\klee silently truncates allocation sizes to \code{uint32\_t}, potentially causing false positives.
