\section{Proof Generation}
\label{sec:proof-generation}

Ultimately, our goal is to prove that the analyzed program is safe.
%\Cref{theorem:safety-via-et} implies that the existence of a safe execution tree guarantees program safety with respect to the concrete semantics.
%This result is crucial, as it provides the foundation for constructing safety proofs.
\Cref{theorem:safety-via-et} guarantees that the program is safe with respect to the concrete semantics if one provides a safe execution tree.
In this section, we show how to compute such an execution tree and how to prove its safety properties.
%Our approach works as an instrumentation of the \SE engine, and we extend it to support memory operations.

The final output of our approach is a \coq proof consisting of two main sections.
%
The first section is manually written and contains general theory,
\ie the definitions and lemmas from~\Cref{sec:concrete-semantics,sec:symbolic-semantics,sec:program-safety}.
%
The second section is generated by the \SE engine and it contains definitions and lemmas that are specific to that program:
module definition, symbolic states, execution tree, \etc
First, we generate the module definition and the proof of the module assumptions.
During the analysis,
we generate the definitions of the symbolic states and the execution tree.
For each instruction executed by the \SE engine,
we generate a lemma that proves the safety property (\Cref{def:safe-et}) for the corresponding subtree in the execution tree.
After we generate the proof showing that the whole execution tree satisfies that safety property, we apply~\Cref{theorem:safety-via-et}.

Here, we present our approach using \klee~\cite{klee}. %, a \emph{state-of-the-art} \SE engine.
% TODO: improve
We note that our approach can be adapted to other \SE implementations as well.
Before diving into the details,
we give background about the memory modeling in \klee.

\subsection{Memory Modeling in \klee}
%In this section,
%we give some background about the memory modeling in \klee.

% TODO: unique interval?
\klee represents the memory as a linear address space of memory objects,
each associated with a concrete base address and a concrete size.
\klee encodes the contents of a memory object using two representations: \emph{optimized} and \emph{non-optimized}.
If all the stores to a memory object were performed with a concrete offset,
\klee uses the optimized representation:
a mapping between constant offsets and symbolic values.
If there is at least one store with a symbolic offset,
\klee uses the non-optimized representation:
an SMT array, \ie a sequence of store expressions.
Once the representation of a memory object is switched to the non-optimized one, it cannot be switched back to the optimized one.

\subsection{Translating Modules and Symbolic States}
\label{sec:proof-translation}
We translate the \llvm module into its corresponding representation in \coq,
and generate a proof showing that the module assumptions are indeed satisfied (\Cref{sec:program-safety}).
During the analysis, we translate the symbolic states generated by the \SE engine into their corresponding representation in \coq (\Cref{def:symbolic-state}).
We translate memory objects from \klee's internal representation into \coq as follows.
In the case of an optimized representation,
we translate the internal mapping $\{0 \mapsto e_0, 1 \mapsto e_1, \ldots\}$ into a sequence of store expressions in \coq:
\[ \arraystore{\arraystore{\arrayconst{\arrayinitvalue}}{\bvconst{32}{0}}{e_0}}{\bvconst{32}{1}}{e_1} \ldots \]
In the case of a non-optimized representation,
we directly translate the internal sequence of store expressions into a sequence of store expressions in \coq.
Accordingly, we translate the internal heap into a list of memory objects in \coq.
}

\subsection{Proving Execution Tree Safety using Interface Lemmas}
\label{sec:proof-et}

The most challenging part in the proof generation process is proving execution tree safety,
which eventually enables proving program safety using~\Cref{theorem:safety-via-et}.
%In this section, we describe in detail how to generate this part of the proof.
To do so, we first generate the definition of the execution tree in a bottom-up manner.
Then, we have to prove that the resulting execution tree satisfies the $\safeet$ relation (\Cref{def:safe-et}).
We generate this proof in a bottom-up manner as well, showing that each subtree satisfies the required relation.
The proof of each subtree corresponds to a single instruction executed during the analysis.
Generating explicit proofs for each individual subtree is expensive in terms of proof generation,
and it also makes the proof checking inefficient,
as such proofs require expensive \coq tactics (\eg \textit{inversion} and \textit{subst}).
Instead, we create for each instruction type a generic lemma that helps inferring execution tree safety.
We call these lemmas \emph{interface} lemmas,
as they facilitate an effective interaction between the pre-defined and auto-generated sections of the proof.
By using such interface lemmas,
we accelerate both proof generation and proof checking,
as we generate smaller proofs that rely on simple \coq tactics (\eg \textit{apply} and \textit{reflexivity}).

\subsubsection{Example: Malloc}
Let $s_0 \triangleq \symstate{\location_1}{\{ \}}{[]}{[]}{\true}$ by the initial symbolic state at~\cref{line:llvm-malloc},
and suppose that we want to prove that the subtree of $s_0$ is safe.
%\[
%s \triangleq \symstate
%    {\location_1}
%    {\{ \}}
%    {[]}
%    {[]}
%    {\true}
%\]
In general, the \rulenameref{Malloc} rule (\Cref{sec:symbolic-semantics}) may derive multiple symbolic states.
Here, however, the size argument of \textit{malloc} is evaluated to a constant SMT expression,
so the only derived symbolic state is:
\[ \mech{s}_1 \triangleq \symstate{\location_2}{\{ \nameid{p} \mapsto \bvconst{64}{\addr} \}}{[]}{[\mobj{\bvval{\addr}{64}}{\bvval{2}{32}}{\arrayconst{\arrayinitvalue}}]}{\true} \]
%\[
%s' \triangleq \symstate
%    {\location_2}
%    {\{ \nameid{p} \mapsto \bvconst{64}{\addr} \}}
%    {[]}
%    {[(\bvval{\addr}{64}, \bvval{2}{32}, \arrayconst{\arrayinitvalue})]}
%    {\true}
%\]
where $\bvval{\addr}{64}$ is the allocated base address.
At this point, the \SE engine uses an optimized representation for the allocated memory object, as no stores have been performed yet,
so the symbolic state computed by the \SE engine is:
\[
s_1 \triangleq \symstate
    {\location_2}
    {\{ \nameid{p} \mapsto \bvconst{64}{\addr} \}}
    {[]}
    {[\mobj{\bvval{\addr}{64}}{\bvval{2}{32}}{\arraystore{\arraystore{\arrayconst{\arrayinitvalue}}{\bvconst{32}{0}}{\arrayinitvalue}}{\bvconst{32}{1}}{\arrayinitvalue}}]}
    {\true}
\]
Now, we have to prove that the subtree of $s_0$ is safe.
Based on~\Cref{def:sym-error-state},
$s_0$ is not an error state since $\evalexprty{2}{\symlocalstore}{\bvsort{64}} = \bvconst{64}{2}$.
To prove that $\mech{s}_1 \equiv s_1$,
it suffices to prove that their memory is equivalent.
The SMT arrays in those two symbolic states are encoded differently,
but they are actually equivalent, since the additional store expressions contain the same value $\arrayinitvalue$ as in $\arrayconst{\arrayinitvalue}$.

To handle the case of \textit{malloc} in general, we define the interface lemma below.
In this case, we can apply~\Cref{lemma:interface-malloc} with $n$ as 2, $\mo$ as the memory object from $s_1$, and $t$ as the subtree of $s_1$.
% TODO: show why the preconditions hold?

\begin{interfacelemma}
\label{lemma:interface-malloc}
Let $s \triangleq \symstate{\location}{\symlocalstore}{\symstack}{\symmemory}{\pc}$,
where \textup{$\instrat{\location} = \codequote{x~\texttt{=}~\tcall^{\pointertypeof{\bvsort{8}}}~\intrinsicfunc{malloc}(\bvsort{64} ~ e)}$},
and let $\bvval{\addr}{64}$ be the allocated base address.
Then $\safeet(\tree(s, [t]))$ if there exist $n$, $\mo$, and $t$ such that:
\begin{enumerate}
    \item \textup{$\evalexprty{e}{\symlocalstore}{\bvsort{64}} \equiv \bvconst{64}{n}$} and \textup{$\bvval{n}{64} < \bvval{(2^{\indexwidth - 1} - 1)}{64}$}
    \item \textup{$\mo \equiv \mobj{\bvval{\addr}{64}}{\bvval{n}{32}}{\arrayconst{\arrayinitvalue}}$}
    \item \textup{$t.\attrstate = \symstate{\nextinstr{\location}}{\symlocalstore[x \mapsto \bvconst{64}{\addr}]}{\symstack}{\symmemory \cup \{\mo\}}{\pc}$} and $\safeet(t)$
\end{enumerate}
\end{interfacelemma}

Note that this lemma assumes that the size argument of \textit{malloc} is evaluated to a concrete SMT expression.
%If that is not the case,
Otherwise, the \SE engine typically concretizes the symbolic expression,
and then the analysis may be incomplete and a safety proof may not be derivable.
There exist \SE engines that support symbolic-size allocations (\eg \cite{uc-klee,symsize-model}),
however, it is not the focus of this work.

Automatically proving such propositions requires reasoning on the level of the concrete semantics, which is challenging in this case.
Instead, we use additional definitions and lemmas that help generating this proof by reducing the problem back to the symbolic semantics.

First, we define the function $\overflowcond$,
which computes an SMT formula encoding the fact that an overflow occurred during the address calculations in $\tgep$.
The pseudo-code of this function is given in~\Cref{alg:symbolic-gep} (function \textsc{compute-overflow}).
The auxiliary functions \textit{trunc\_overflow}, \textit{mul\_overflow}, and \textit{add\_overflow} are used to handle overflows for specific operations.
For example, \textit{trunc\_overflow} returns an SMT formula encoding the fact that the truncation does not preserve the unsigned value.
For brevity, the definitions of these functions are omitted.\footnote{
The full definitions of these functions can be found in our \coq framework.

The following lemma helps to connect between the concrete evaluation of the $\evalgep$ function and the overflow constraint generated by the $\overflowcond$ function.
\begin{lemma}
Let $\tau$ be a type, $p$ a pointer value of type $\bvsort{\pointerwidth}$, and $\overline{t_i}$ a sequence of SMT expressions.
If $\evalgep(\tau, p, \overline{m[t_i]}) = \tpoison$,
then $m \models \overflowcond(\tau, \overline{t_i})$.
\end{lemma}

Now, based on this lemma,
we can prove that $s_7$ is not an error state by proving that the constraint $\overflowcond(\bvsort{8}, \bvzext{64}{n})$ is unsatisfiable.
More specifically, we need to prove the unsatisfiability of the following constraint:
\[
n < \bvconst{32}{2} \land \big((\bvzext{64}{n} > \bvconst{64}{(2^{32} - 1)}) \lor (\bvmul{\bvsort{64}}{\bvzext{64}{\bvsext{32}{\bvzext{64}{n}}}}{\bvconst{64}{1}}) > \bvconst{64}{(2^{32} - 1)}\big)
\]
%which is indeed unsatisfiable.
Rather than generating an explicit proof of unsatisfiability for this query,
we include the SMT solver in the trusted computing base,
and axiomatize the unsatisfiability of the corresponding query generated by the \SE engine.
Then, to prove that the query above is unsatisfiable,
we leverage our simplification theory (\Cref{sec:example-store}) to establish its equivalence to the axiomatized query.

To handle the case of \textit{getelementptr} in general, we define the following interface lemma:

\begin{interfacelemma}
\label{lemma:interface-gep}
Let $s \triangleq \symstate{\location}{\symlocalstore}{\symstack}{\symmemory}{\pc}$,
where \textup{$\instrat{\location} = \codequote{x~\texttt{=}~\tgep~\pointertypeof{\tau}~e~\overline{(\tau_i, e_i)}}$}.
Then $\safeet(\tree(s, [t]))$ if there exist $\overline{k_i}$, $\symlocalstore'$, and $t$ such that:
\begin{enumerate}
    \item $\evalexprty{e_i}{\symlocalstore}{\tau_i} = k_i$ and $\unsat{\pc \land \overflowcond(\tau, \overline{k_i})}$
    \item \textup{$\symlocalstore[x \mapsto \evalexprty{\tgep~\pointertypeof{\tau}~e~\overline{(\tau_i, e_i)}}{\symlocalstore}{\tau^{*}}] \equiv \symlocalstore'$}
    \item $t.\attrstate = \symstate{\nextinstr{\location}}{\symlocalstore'}{\symstack}{\symmemory}{\pc}$ and $\safeet(t)$
\end{enumerate}
\end{interfacelemma}
