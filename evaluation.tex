\section{Evaluation}
\label{sec:evaluation}

In this section, we evaluate the applicability and effectiveness of our approach.
The following research questions guide our evaluation:
\begin{itemize}
    \item \textbf{RQ1}: Can our approach generate valid safety proofs?
    \item \textbf{RQ2}: What is the overhead of proof logging during symbolic execution?
    \item \textbf{RQ3}: What is the cost of validating the generated safety proofs?
\end{itemize}

\textbf{\textit{Setup.}}
We evaluate two modes:
\proofopt is our proof-logging approach, and \base is vanilla \klee~\cite{klee}.
Each mode is run with the DFS search heuristic, an one-hour timeout, and a 4GB memory limit.
%and the SMT solver is set to STP~\cite{stp}.
We measure the following metrics:
analysis time, number of explored paths, and number of executed instructions.
In the \proofopt mode,
we also measure the \emph{proof time}, \ie the time required to validate the generated proof using \coqc,
and the \emph{proof size}, \ie the size of the generated proof file (\code{.v} file).
We performed our experiments on Ubuntu 24.04,
equipped with Intel Core i9-9900 and 32GB of RAM.

\textbf{\textit{Benchmarks.}}
%Our implementation supports memory operations,
To evaluate our approach,
we selected memory-manipulating programs that do not invoke external calls,
as our framework currently does not model the environment (command-line arguments, file system, networking, \etc).
%Our implementation supports memory operations,
%so our goal is to evaluate it on memory-manipulating programs.
We chose several benchmarks that were used in the past in the context of \SE~\cite{klee,symsize-model,compact-s-e,pinaka,klee-rocq}:
\libtasn~\cite{libtasn1}, \libosip~\cite{libosip}, \coreutils~\cite{coreutils-misc}, and \svcomp~\cite{svcomp}.
We selected a set of APIs from \libtasn, \libosip, and the library of \coreutils,
and for each API we constructed a test driver that runs it with symbolic inputs (\eg integers, arrays, and strings).
%In \libtasn and \libosip, we selected a set of APIs,
%and for each API we constructed a test driver that runs it with symbolic inputs (integers, arrays, strings, \etc).
%To symbolically execute the programs in \coreutils,
%one needs to support external calls and model the environment (command-line arguments, file system, \etc).
%As our implementation currently does not support these features,
%we could not evaluate those programs directly.
%However, \coreutils contains a library of APIs, some of which can be tested in isolation.
%We selected a subset of such APIs,
%and constructed test drivers that run these APIs with symbolic inputs.
In \svcomp, we selected a subset of programs from the \textit{array-memsafety} category.
Since some programs in that category are intentionally unsafe,
we restricted our selection to safe programs, \ie those that can be verified in principle.
Most of these programs perform memory allocations with symbolic sizes,
which are currently unsupported by both \klee and our approach.
To overcome this, we modified the relevant parts in these programs to perform fixed-size memory allocations instead.
In total, our evaluation comprises 42 subjects.
The average subject size is 127 \llvm IR instructions, with a maximum of 548 and a minimum of 33.

\paragraph{\textbf{\text{RQ1.}}}
Our approach was able to generate valid proofs for all the subjects,
which means that those programs are safe w.r.t. the concrete \llvm semantics formalized in~\Cref{sec:concrete-semantics}.

\paragraph{\textbf{\text{RQ2.}}}
To evaluate the overhead of proof logging during the symbolic execution,
we compare the analysis times of \proofopt and \base.
The results are shown in the scatter plot from~\Cref{figure:time},
where the x-axis and y-axis represent the analysis times with \base and \proofopt, respectively.
The average slowdown is 1.33\x and the median slowdown is 1.26\x.

\paragraph{\textbf{\text{RQ3.}}}
The scatter plot from~\Cref{figure:proof-time-size} shows the proof time and the proof size for each subject.
The average and median proof times are 119.5 seconds and 23.1 seconds, respectively.
The average and median proof sizes are approximately 15,000 KB and 5,000 KB, respectively.
% TODO: improve
In general,
as the number of executed instructions increases,
the size of the generated proof increases as well,
which in turn results in higher proof time.
There were two cases (\textit{test\_osip\_hash} and \textit{test\_hash\_pjw}) in which the proof time was rather high despite the number of executed instructions being relatively low.
This occurred due to the presence of complex SMT array terms in the definitions of the symbolic states and in the application of the interface lemmas for $\tload$ and $\tstore$.
We leave the optimization of such cases for future work.
